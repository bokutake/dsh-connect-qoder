# magpie #330：一次任务 265 次请求后触发「Billing daily count exceeded」

> **来源**：这是**另一个仓库**的 issue ——
> [`magpie-community/plugins#330`](https://github.com/magpie-community/plugins/issues/330)，
> 不是本仓库的编号。文件名带 `magpie-` 前缀就是为了不与本仓库 `dingminhua/dsh-connect-qoder`
> 的 issue 编号混淆（本仓库的 issue #330 是另一件事，或者还不存在）。
>
> **为什么要在这里落盘**：那份 issue 提出的问题与本插件 1.28.0 修的缺陷指向同一个根因，
> 而它给出的结论边界不清。把对照写下来，一是给维护者一个可核验的参照，二是避免日后有人
> 拿「magpie 说已经修了」当成本插件也已验证的结论。

## 一、issue 说了什么

标题原文：

> qoder: 一次 DSH 任务 265 次请求后触发 "Billing daily count exceeded"，怀疑每条请求都被
> 记成一次新对话

要点：

1. 一次 DSH 任务产生了 **265 次请求**，之后撞上 `Billing daily count exceeded`；
2. 作者（`real-jacket`）的推断是「每条请求都被记成一次新对话」，于是日计数按**请求数**
   而不是按**对话数**累计，很快就超限；
3. 维护者（`yetone`）在 magpie `0.2.31` 里做了修复；
4. 作者的复测结论：**不再出现该报错**，但补充说明计数语义「查不到，也没用真实账号测过」。

## 二、我们的实测结论

对官方 CN CLI（`qoderclicn` 1.1.94）做 MITM 抓包，两次共 80 个请求，结论与 issue 的
**推断方向一致，但定位更靠下**：

| 层次 | issue 的假设 | 实测结论 |
| --- | --- | --- |
| 计数单位 | 每条 HTTP 请求 = 一次对话 | **每轮用户提示 = 一条 `business` 记录**；轮内 N 次补全共用 1 个 `id`，只 1 次闭合 |
| 触发原因 | 265 次请求 → 265 条对话 → 超限 | 不只是「请求多」，而是**每条记录都没闭合**：服务端只能等 TTL 释放租约与日计数 |
| 修复层次 | 不在 issue 里 | 既要按轮回并，**也要在轮末发 `business/finish`** |

支撑数据：

- 一轮 1 次补全（无工具）→ **1 次** `business/finish`；
- 一轮 2 次补全（含 1 次 `Bash` 工具调用）→ **仍然 1 次** `business/finish`；
- 两笔补全的请求体从 155 648 B 涨到 157 648 B（工具结果在轮内累积），闭合次数不变；
- 恢复旧会话后第二轮 → 1 次补全、1 次闭合。

也就是说：**issue 猜的「每条请求一次对话」在官方客户端里不成立** —— 官方是按轮来的。
真正让日计数膨胀的是「记录创建了却永不闭合」，而不是「请求次数多」。

## 三、和 magpie 实现的对照

| 项 | 官方 CLI | magpie 0.2.71 | 本插件 1.28.0 |
| --- | --- | --- | --- |
| `business.id` 粒度 | 每轮用户提示 | 每轮用户提示（`sha256([sid, lastUserIndex, lastUserContent])`） | 每轮用户提示（`session_id` + 本轮用户提示） |
| 记录上限 | — | `TASK_MAX = 512`、`TASK_IDLE = 2h` | `STAGE_MAP_LIMIT = 512`，闭合即删 |
| `business/finish` | **发**（每轮 1 次） | **不发**（注释说靠服务端 TTL） | **发**，响应 `success` |
| 终态 `stage` | `init → start → processing → complete` | `start` / `processing` | 同官方，含终态 |

**所以「本插件在计数语义上比 magpie 更完整」这句话是有依据的**：magpie 把计数单位改对了
（这一步它是对的，也是 0.2.31 修的东西），但没有补闭合 —— 记录仍然永不收口，只能等服务端
TTL。本插件两环都补了。

## 四、结论边界（**重要**）

**本插件没有验证「`Billing daily count exceeded` 不再出现」。**

必须把这条写清楚，否则这份文档会被读成比实际更强的结论：

- **已验证**：每轮只产生一条记录、一次闭合；闭合被上游接受（响应 `success`）；计费控制台
  确实出现**逐条消费行**，时间戳与抓包逐条对得上。
- **未验证**：那个报错是**日累计**触发的，需要跑到当日上限才会重现。验证期间只跑了几轮，
  远不到上限。本机控制台**没有暴露日计数**（只有逐条消费行），连间接读数都没有。

推论方向是清楚的（日计数超限最可能的成因是大量记录永不闭合），但**它仍是推论**。

同样地，magpie 那边「0.2.31 之后不再报错」这个结论，其作者自己也说明没有用真实账号验证过
计数语义。**两边都缺直接观测** —— 差别只在于本插件补上了 magpie 没有的那一环。

要把这条变成验证过的结论，需要一次「跑到当日上限」的实测。在那之前，这一项在
[`CHANGELOG.md`](../../CHANGELOG.md) 的「明确未验证」一节里保持标记。

## 五、复现与取证方法（不含凭据）

本仓库**不收录**抓包文件与脚手架：`captures/` 里含真实的 `cosy-key`、`cosy-machinetoken`
与 bearer 载荷，等价于会话凭据。可信的替代做法是自己抓一次，判据如下：

1. 抓包观察 `POST /algo/api/v2/service/business/finish?Encode=1` 的**次数**；
2. 让一次用户提示触发工具调用（一轮内多次补全），确认补全次数 > 1 而闭合次数 == 1；
3. 解 `Encode=1` 请求体，确认明文是 `{"payload":"<JSON 字符串>","encodeVersion":"1"}`；
4. 对照 `business.id` 在轮内稳定、跨轮变化。

请求头层面的对照值（`cosy-clienttype: 5`、`cosy-business-product: cli`、`Bun/1.4.4` 等）
与实测结果见 [`CHANGELOG.md`](../../CHANGELOG.md) 的「实测验证」一节。
